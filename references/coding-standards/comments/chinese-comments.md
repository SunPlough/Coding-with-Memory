# 中文代码注释规范

注释只保存代码本身无法稳定表达的信息，不追求注释数量。

## 1. 选择注释语言

1. 依次检查仓库规则、贡献文档、相邻文件、生成工具要求和公共 API 受众。
2. 保持模块既有语言。不要向英文模块突然加入中文，也不要在功能修改中翻译无关注释。
3. 全新中文团队项目没有既有政策时，解释性注释可使用简体中文；标识符、API、协议字段、命令和错误码保留原文。
4. 国际公共 API、上游贡献政策、代码生成器、Lint 或生态惯例要求英文时使用英文。
5. 不要中英文重复表达同一句话。

注释语言是项目编码决策。Memory 可以记录仓库中已批准的决定，但个人偏好不能覆盖它。

## 2. 记录契约或原因

注释至少应保存以下一种事实：

- 公共契约：用途、输入约束、返回含义、错误、副作用、兼容性、线程安全或废弃行为；
- 代码中看不出的业务规则及其来源或原因；
- 不变量、单位、范围、边界、顺序规则或状态转换；
- 非显然的算法选择，以及为何没有采用更简单方案；
- 并发、安全、性能、协议、迁移或兼容性约束；
- 必须保留的特殊路径、权宜方案或看似多余的操作；
- 不能通过命名消除的正则、位掩码、魔法值、外部字段映射或生成边界。

公共文档注释描述调用者能够依赖的可观察契约；内部注释解释实现为什么必须如此。例行机制交给命名、类型和代码表达。

添加注释前，依次尝试：改进命名、提取聚焦函数、简化条件、引入命名常量、用类型或测试建模。仍无法表达的信息才写入注释。

## 3. 禁止内容

- 对下一行的中文翻译，例如在循环前写“遍历用户列表”；
- 重复函数名、参数名、类型标注或显然返回表达式的注释；
- 由版本控制记录的编辑历史、个人归属、日期或版本；
- 被注释掉的旧代码，应删除并从版本控制恢复；
- 没有 Issue、规范、测试或仓库证据支持的未来分支与兼容需求；
- 没有工具要求的大型文件头、装饰分隔符和样板文本；
- 用注释掩盖本可简化的代码；
- 密钥、令牌、凭据、客户数据、私人地址、真实个人数据或完整敏感请求/响应。

不要强制每个私有函数、简单 getter、构造器、字段或常量都有文档注释。语言规范或仓库可能对公共 API 有更严格要求。

## 4. 清晰书写中文

- 直接说明主体、约束与原因。三者都重要时可使用“因 X，必须 Y，否则 Z”。
- 使用具体名词，避免没有说清条件的“这里进行处理”“相关逻辑”“特殊情况”。
- 中文句子使用简体中文标点；标识符、路径、命令、字段、单位和 Issue ID 保持精确。
- 同一领域概念使用同一术语，不来回更换译法。
- 一条注释聚焦一个问题。长篇架构或运维背景应移到 ADR/设计文档，并链接稳定仓库引用。
- 不声称未观察到的原因、所有者、标准、Bug 或性能结果。

好例子：

```python
# 结算日按商户时区判断，避免 UTC 跨日后重复生成账单。
settlement_date = now.astimezone(merchant.timezone).date()
```

坏例子：

```python
# 获取当前时间并转换时区，然后获取日期。
settlement_date = now.astimezone(merchant.timezone).date()
```

好例子：

```java
// 上游可能重试同一事件；先写入幂等键，防止重复扣减库存。
idempotencyStore.reserve(event.id());
```

## 5. 放置与维护

- 解释性注释放在其约束的最小代码块正上方，并保持相同缩进。
- 行注释标记后留一个空格，除非语言或工具要求其他格式。
- 除仓库既有的短单位或字段映射外，避免行尾注释。
- 公共契约采用语言要求的文档注释，内部原因采用普通行注释。
- 行为变化时在同一补丁更新或删除相邻注释；过期注释属于缺陷。
- 审查时对照最终代码、测试、Issue/规范和支持版本验证内容。

## 6. 延迟工作标记

仅在仓库允许时使用，并确保可操作、可追踪：

```text
TODO(PROJ-123): 说明剩余工作、当前阻塞原因和完成条件。
FIXME(PROJ-456): 说明已知错误、影响范围和预期修复方向。
HACK(PROJ-789): 说明为何必须绕过、风险以及删除条件。
```

- 使用真实 Issue 或仓库定义的所有者格式，严禁虚构编号。
- 不写裸 TODO/FIXME，不把标记当永久文档，也不能推迟当前安全或正确性要求。
- 解释过长且难以同步时使用 Issue 或设计文档。

## 7. AI 注释门禁

交付 AI 生成代码前，审查每条新增或修改注释：

1. **证据**：内容是否由代码、测试、Issue/规范或已观察约束支持？
2. **价值**：是否增加了命名、类型和代码无法表达的契约或原因？
3. **范围**：是否附着于最小相关代码单元？
4. **格式**：是否采用所选语言文档语法和仓库注释语言？
5. **时效**：编辑结束后是否仍描述最终实现？
6. **隐私**：是否没有秘密和私人数据？
7. **复杂度**：小型重构是否能消除这条注释？

删除或改写未通过门禁的注释，不要通过增加更多注释来“达标”。
