# 通用工程基线

本文件是所有语言的共同层。语言文件负责语法、命名和工具细节；项目规则可以在此基础上收紧，但不能用用户偏好绕过安全和质量要求。

## 规范等级

语言规则使用以下词汇，避免把建议误读成无条件禁令：

- **MUST**：上游明确要求、工具必需或项目已批准的硬约束。
- **SHOULD**：Google/官方推荐；有证据的例外必须写在 diff 或项目覆盖规则中。
- **MAY**：规范允许的选择；优先保持同文件和同目录一致。
- **AVOID**：上游明确不推荐或会增加风险；只有当前需求、性能证据或兼容性要求才能例外。

## 必须遵守

- 采用满足明确需求的最小完整变更。
- 匹配仓库已有结构、命名、错误模型、日志方式和测试惯例。
- 一次变更只处理一个逻辑关注点；功能开发与无关重构分开。
- 在输入、I/O、网络、持久化、并发和外部 API 边界显式处理失败。
- 不记录密钥、令牌、凭据、个人数据或完整敏感请求/响应。
- 为改变的行为和重要边界新增或更新测试，不以提高覆盖率数字为唯一目的。
- 按项目包管理策略锁定或约束依赖，并说明兼容性影响。
- 记录公共 API、迁移、配置和运维行为变化。
- 遵循 [注释规范](comments/index.md)：注释保存契约与原因，不逐行翻译代码。

## Google 风格落地协议

1. 先用 `language-map.yaml` 识别文件语言；`.h` 必须先判断 C 或 C++。
2. 加载 `base.md`、一个语言文件、注释规范和适用框架/项目覆盖；不要批量加载无关语言。
3. 先运行仓库已有 Formatter/Lint，再人工处理工具无法表达的契约和边界。
4. 新代码必须满足当前语言文件的 MUST；旧代码只在本次变更触及范围内渐进修正，避免制造无关 churn。
5. 规则未覆盖的选择遵循同文件、同目录和仓库惯例；仍无法确定时保留最小选择并记录假设。

## 复杂度门禁

- 没有当前用例，不新增抽象、分支、配置、扩展点、重试或回退路径。
- 早返回能减少嵌套并提高可读性时优先使用，但不机械追求分支指标。
- 先保持行为正确，再改进风格；不顺手重写无关代码。
- 小型重构能消除歧义时，优先改进命名、类型和结构，而不是堆叠解释性注释。
- 新通用层至少说明两个当前、稳定且真正重复的使用场景。
- 通用建议与仓库规则冲突时遵循仓库规则，并记录原因。

## 验证

运行变更路径适用的格式检查、Lint、类型/构建、测试和安全/依赖检查。所有格式化器必须使用检查模式；报告跳过、未发现和失败的检查及原因。没有工具时，使用本目录的定向规则审查，并明确标注 `not-found`，不能声称已通过。
